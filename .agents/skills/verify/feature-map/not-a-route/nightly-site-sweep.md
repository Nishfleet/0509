The first read is the baseline. An identical hash stores nothing else. A different hash stores the new text and a 1440×900 screenshot under `snapshot/site/`. Screenshots are budget-capped at 4 per brand per day; past the cap the change still publishes with `screenshotKey` null. **Publish**, a separate retried step: decode the page's character codes (`&amp;`, `&#x27;`, `&mdash;`: `decodeHtmlEntities` in `app/lib/html.ts`) in both texts and, when they read the same, file nothing (`site.change_same_text`); when a competitor's page other than pricing goes back to a text any of its snapshots showed in the last 14 days (a banner or locale flipping back), file nothing (`site.change_flap`, `hashSeenSince` in `app/lib/data/snapshot.server.ts`, proof in `tests/integration/site/sweep.integration.test.ts`); otherwise word-diff the two texts, store the hunks as `<snapshot>.diff.json`, and write one `signal` with `kind = 'change'`, `aspect` = the page role, `dedup_key` = the snapshot id (so a retried step files nothing twice), and `payload_json` naming the before and after snapshots, text keys, screenshot keys, diff key and word counts. A page that cannot be read fails alone and logs `site.check_failed`; a step that still throws after its retries is logged as `site.sweep_step_failed` and the sweep moves on. The snapshot id is `<instance>-<page>` and "previous" means the latest snapshot from before this run started, so a retried check files the same change again instead of losing it. The judge's `history_30d` carries, for the five newest earlier changes of the brand, the wording of each (`Sort: Relevance → Sort: Featured`, read from its stored diff), so a rotating banner or flip-flopping control reads as a repeat (`tests/integration/site/judge.integration.test.ts`, case g3). Changes are not yet judged by Jev D3, so the standing's noteworthy bucket does not count them; the brief's counts line does. **Record:** a `record` step writes one `sweep_run` row per finished sweep — instance id, planned and finish times, wall clock in ms, pages and failed counts (`app/lib/data/sweep_run.server.ts`, migration `0029`) — through the file's `settle` so a bookkeeping write cannot fail the run or suppress the ping. **Report:** the Workflow's last step, `report`, POSTs to `SITE_SWEEP_PING_URL` through `pingLiveness`. An external check (24 h period, 2 h grace) alerts when a night's sweep never finishes. When the var is unset, it sends nothing. A filed site change also carries `excerpt` in its payload (up to 4 hunks of 20 lines, 240 characters a line, `app/lib/site-change-excerpt.ts`) so the before and after wording can be read from D1 without R2; the nightly job fills it in for older changes, 100 a night (`backfillChangeExcerpts`, `app/lib/site/backfill-excerpts.server.ts`), and marks a change whose diff is gone with an empty excerpt. Proof: `tests/integration/site/sweep.integration.test.ts`, `tests/integration/sweep-run.integration.test.ts`, `tests/integration/hot-path-indexes.integration.test.ts` and `tests/integration/site/check-page.integration.test.ts`. Shared work across workspaces (off in production: the `SHARED_RIVAL_CHECKS` var in `wrangler.jsonc` is `off` until the site-change eval passes, and each shared lookup logs a `site.shared_check` line): a competitor's page is read once per sweep run and the page text is kept in `IDENTITY_CACHE` (key `shared-read:<sweep time>:<fetch or browser>:<hash of the URL>`, 36 hours, only `html`, `transport`, `status`, `ms`; `app/lib/fetch/shared-read.server.ts`, called from `readPage`), so the next workspace watching the same URL that night reuses it (only when the first read ended on the transport it started with, so a copy got by escalating to the browser is never handed to a workspace that did not pay for it) instead of fetching again; the owner's own pages are never shared, and every workspace still writes its own snapshot, diff and signal.
