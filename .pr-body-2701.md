## What

The `Verify and pin exact main candidate` step (`id: pin`) in the `pin_candidate` job of `.github/workflows/deploy-production.yml` was the **only** caller of `scripts/ci-verify-production-candidate.sh` without `TOLERATE_MAIN_DRIFT: "1"`. When main advanced while a Deploy-production run was queued, the pin CAS failed `production_candidate_invalid: provider_main_cas` (`remote_main_drift`), the run went red, and each red run filed a fresh `AUTO-REVERT HALT` (71 open as of 2026-09-10T21:35Z).

This PR adds `TOLERATE_MAIN_DRIFT: "1"` to the pin step's `env:` — the same setting the four later steps in the same workflow already carry. `scripts/ci-verify-production-candidate.sh` is untouched.

## Why this does not weaken the gate

The pin's CAS still verifies `PINNED_SHA` itself, and the CAS script's ancestor logic is preserved:

- **workflow_dispatch:** the CAS enforces that the dispatched candidate is an ancestor of live main (existing branch) — fail-closed on rewind/rewrite.
- **push events:** `PINNED_SHA` was the main tip at run creation; remote main can only have advanced from it, so the SHA that ships is always an ancestor of live main. The tolerate branch merely records the forward move.
- Every other CAS failure (provider API unavailable, wrong repo/ref, malformed SHA, rewind/rewrite of main) stays fail-closed.

So no SHA that is not an ancestor of current main can ever reach the tolerate branch and ship.
