## Root cause (the #3336 self-heal is unreachable in production)

#3336 provisioned + repaired the proof-email target at the END of `ensureCanaryTarget` — after the early return:

```ts
const existing = await getCanaryTarget(env, canaryEmail);
if (existing) return { target: existing, provisioned: false };   // ← provisioning dead here
```

The watchlist half of the substrate persists across failed deploys (cleanup only runs after a fully green gate, and none has been fully green since 2026-09-09), so on every real deploy the early return fires and the 2026-09-11 provisioning gap — user + watchlist created, **no delivery_target** — is never healed. `deliverWeeklyDigest` then resolves the canary owner's email targets with `requireUniqueExistingTarget: true`, finds zero usable rows, and throws `Gate C proof email target must resolve uniquely.` (`app/lib/delivery.server.ts:318`) → 503 `canary_proof_pipeline_failed`. Same mechanism explains #3336's red tests: the guard-route test exercises exactly the existing-substrate shape, where the convergence never ran (`provisionVerifiedAccountEmailTargetIfUnsuppressed` calls: 0, proofEmail `ok:false`).

## Fix (substrate convergence, both paths — the gate is untouched)

Extract `ensureCanaryProofEmailTarget(env, userId, canaryEmail)` (`provisionVerifiedAccountEmailTargetIfUnsuppressed` INSERT-OR-IGNORE + `repairCanaryProofEmailTarget`) and call it on **both** outcomes of `ensureCanaryTarget`:

- watchlist substrate **exists** → converge the proof-email half before returning (this is the production deadlock);
- substrate created fresh → same calls, now via the shared helper.

Both steps are idempotent, so steady state costs a few reads. No test skipped, no gate weakened — `requireUniqueExistingTarget` itself is unchanged.
