## What and why

The landing-page CTA-change detector was near-silent (4 events in 4 months across 88 watchlists, last 2026-06-15) and there was no queryable per-stage counter to show which gate was dropping the signal. The pipeline already emits a per-check JSON log line (`landing_page_pipeline_check`), but that log is not queryable in D1.

This PR makes the per-stage funnel queryable:

- **Migration `0083_cta_pipeline_stage_counts.sql`** — a new additive `cta_pipeline_stage_counts(day, stage, count)` table (PK `(day, stage)`), one-way (expand/contract): no column or table is dropped or renamed, no `NOT NULL` without a `DEFAULT`.
- **`app/lib/cta-pipeline-stage-counts.server.ts`** — derives the six accept-criteria stages (`checks_started`, `page_fetch_succeeded`, `validity_passed`, `dom_extracted`, `diff_computed`, `event_emitted`) from the existing pipeline counters and upserts them per UTC day. Pure mapping (`ctaPipelineStageCountsFromCounters`) plus a best-effort D1 write (`recordCtaPipelineStageCounts`) that never throws.
- **`app/lib/monitoring.server.ts`** — wires the recording into both landing-page proof-capture paths' `finally` blocks, so every check (success, bail-out, or thrown error) is counted.
- **`tests/integration/cta-pipeline-instrumentation.integration.test.ts`** — regression guard against real D1.

The 72h live 20-competitor cohort run (accept criterion 3) is a live verification that cannot run inside a PR; the counter table and the recording path it needs are what this PR ships. The `event_emitted/checks_started` ratio is now queryable via:

```sql
SELECT stage, SUM(count) FROM cta_pipeline_stage_counts
WHERE day >= date('now','-3 days') GROUP BY stage;
```
