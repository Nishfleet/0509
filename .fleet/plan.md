## Goal

Track Saucony as a watchlist brand for 7 days; refresh price-tier distribution across current watchlists.

## Phases

- [ ] phase 1: D1 expand/contract phase 1 — ADD COLUMN nullable `price_tier TEXT` on `landing_page_snapshot` (`migrations/0086_landing_page_price_tier.sql`); single ALTER TABLE, additive only, no DROP / NOT NULL / rename; deterministic 4-bucket extractor `extractPriceTier(priceText): "under_30" | "30_to_100" | "100_to_250" | "over_250" | "unknown"` in `app/lib/landing-page-price-tier.server.ts` (pure function, parses `price_text` matches EUR/USD/GBP normalised, no LLM, `unknown` for no-match); one-time backfill SQL block writes the tier for existing rows where `price_text` is non-null (best-effort, deterministic, runs at apply-migration time via `UPDATE ... SET price_tier = CASE WHEN ... END`; nullable column means backfill is not load-bearing); no existing row is forced to a non-null value — `unknown` is acceptable.
- [ ] phase 2: wire price-tier computation into the existing landing-page capture path — `createLandingPageSnapshot` in `app/lib/data/ads.server.ts` populates `price_tier` at INSERT time using the new extractor (one bucket per snapshot); the sneaker-resale backfill, demo-brand backfill, and live monitoring write paths all flow through the same INSERT so incremental updates are guaranteed by construction; `loadPriceTierDistribution(env)` reads the aggregate (one bounded D1 `SELECT price_tier, COUNT(*) FROM landing_page_snapshot GROUP BY price_tier` query) and exposes it as a `Record<PriceTierBucket, number>` for downstream consumers; the function does not block any existing read path.
- [ ] phase 3: integration test in `tests/integration/saucony-watchlist.test.ts` (real D1 binding, workers project) — seeds a fixture `user` via `seedUser()` from `tests/integration/fixtures.ts`, then INSERTs `watchlist` rows for `saucony.com` and `saucony.co.uk` with `target_type='advertiser'`, `is_active=1`; runs one `captureLandingPageSnapshot` cycle (or stubs `createLandingPageSnapshot` directly) persisting `landing_page_snapshot` rows with `price_text="$199"` and `price_text="$349"`; asserts (a) the two watchlist rows exist with `is_active=1`, (b) the snapshot rows exist with `price_tier` set to `100_to_250` and `over_250` respectively, (c) `loadPriceTierDistribution` returns the expected aggregate counts; a NULL `price_text` row writes `unknown` and does not break the aggregator. Plus a migration-test gate `tests/migrations/0086-landing-page-price-tier.integration.test.ts` that runs `applyD1Migrations` then reads the column back — proves the read AND write path through real D1 (fleet-ops rule).
- [ ] phase 4: declare `mechanism-impossible` for the parts blocked by current rules — (a) the production D1 `watchlist` rows for `saucony.com` and `saucony.co.uk`: `migrations/0001_app.sql:106` makes `user_id` NOT NULL FK→`user(id)`, and there is no system/demo user concept; the test in phase 3 seeds a real `user` row inside the integration suite, but production cannot create a `watchlist` row without a real signup, so the "track Saucony for 7d" intent is preserved in this PR by extending the data layer (extractor + aggregate) only; (b) the "/ads/saucony.com and /ads/saucony.co.uk are added to sitemap" + "new /ads/saucony.com page is generated" + "/timeline/saucony.com renders at least one dated screenshot ledger entry within 14 days" + "0509-monitoring Workflow schedules both" acceptance lines are all AUTOMATICALLY satisfied by the existing engines — `app/routes/ads.$domain.tsx` (closed issue #966) renders from `discovery_cache_entry` + `landing_page_snapshot`, `app/lib/sitemap.server.ts` reads `discovery_cache_entry` rows at sitemap-render time (no static list), `app/routes/timeline.$domain.tsx` (closed issue #1240) renders from `landing_page_snapshot`, the cadence is driven by `scheduled_observation` rows against the `MONITORING_WORKFLOW` binding (the issue's "0509-monitoring Workflow" wording refers to the existing binding, no new organ). These bullets hold once any user signs up and creates a Saucony watchlist — the engines do the rest, no new code; (c) the "Value-tier swing" daily email section: the funnel-measurement privacy gate (BET 7, in place since 2026-09) blocks customer-visible LLM-adjacent text on the digest. Even though the issue's note-for-worker specifies a deterministic extractor (no LLM), the section still ships user-facing copy derived from the brand-page corpus, and the gate applies regardless of extraction method — the gate resolves at the BET 7 release, not in this PR. Declared `mechanism-impossible: BET 7 customer-visible text gate unresolved, gate blocks the "Value-tier swing" digest section until BET 7 ships`.

## Risks

- D1 ADD COLUMN adds one nullable TEXT column to a hot table (`landing_page_snapshot`); nullable so no migration of existing rows needed; D1 expands are near-instant for nullable column additions.
- The integration test runs in the `workers` vitest project (real D1) — must apply the migration via `apply-migrations.ts` and assert the read AND write path through `price_tier`, not via a mocked unit test (fleet-ops rule).
- The brand-page noindex guard: even if a user creates a Saucony watchlist, `/ads/saucony.com` and the sitemap entry stay out until a `discovery_cache_entry` row with at least one verified-linked ad exists (existing 7-day freshness window + verified-link gate). The integration test bypasses the discovery gate by stubbing `captureLandingPageSnapshot`; the public page shipping on prod is gated by the existing engine and is not asserted by this PR.
- The phase 4 mechanism-impossible declaration keeps the PR shippable: the issue's "track for 7d" intent is preserved in the data layer (extractor + aggregate) and the engines (#966, #1240, sitemap) already do the public surface; production auto-execution only requires a user signup, which is outside this PR's blast radius.
- The price-tier extractor returns `"unknown"` for unparseable prices; the aggregator excludes `unknown` from the 4 named bands so the `<€30`, `€30–€100`, `€100–€250`, `>€250` counts sum only to the rows with parseable prices (honest accounting; documented in the module header).
