## BET 1: Digest re-ranking — landing_page_* leads, ad churn collapses, instant alerts are a landing-page privilege

Implements issue #1483. The digest-builder re-ranking (landing_page_* headline items, ad_new/ad_inactive collapsed to a counted footnote) already shipped on main; this PR closes the two remaining acceptance gaps:

1. **Instant alerts are a landing-page privilege only** (accept #3). `clearsInstantRule` in `app/lib/delivery-policy.server.ts` now gates on the same why-this-matters score that orders the brief: a landing_page_* event fires an instant alert only when `type weight + importanceScore` clears the per-mode threshold (mathematically identical to the prior `importanceScore >= gate` for landing events), and every non-landing type — `ad_new`, `ad_inactive`, `website_page_*` — is never instant-eligible regardless of score or sensitivity mode. Bare ad churn can never interrupt the customer; it only reaches the counted digest footnote.
2. **Rendering-level regression test** (accept #5) at `tests/digest-ranking.test.tsx`. It constructs a mixed event batch (6 landing_page_* + 6 ad churn), renders the brief via `buildDigestEmail`, and asserts the ≥60% landing_page_* headline share, the single counted churn footnote, zero instant alerts for bare `ad_new`/`ad_inactive` (even at max importance in aggressive mode), the landing-page-only instant-alert allowlist, and the all-quiet heartbeat still firing on a zero-landing-page window.

New helpers in `app/lib/digest-rerank.ts`: `whyThisMattersScoreForRecord` (type weight + importance for a live `WatchEventRecord`) and `landingPageTypeWeight`.
