## 1. Loader parallelization (PERF-1, `3189240`)

Audited every route loader under `app/routes` for sequential awaits of
independent D1/API calls. Fixed nine; each entry shows the await-chain shape
(auth/session step omitted).

| Route | Before | After |
| --- | --- | --- |
| `app.dashboard` | wave(11) → wave(5) | one wave(16); `recentChanges` chains its any-active gate off the in-flight watchlists promise |
| `app.watchlists` | wave(4) → emailVerified → getWatchlist → wave(12) | wave(6) → wave(12); `?watchlist=` deep links fetch the selected watchlist fully concurrently. The dossier was verified already inside the second `Promise.all` (not serial) |
| `app.collections` | wave(2) → getCollection → items | one wave; items fetched alongside the ownership check and discarded unless it passes |
| `app.account` | 6 serial lookups | one wave, same per-section failure fallbacks |
| `app.team` | plan → members | one wave |
| `app.support` | cases → case → events | one wave (all reads user-scoped; events discarded on a miss) |
| `app.reports` | preparedBy → pdfGate → loadReport | one wave (after the plan gate) |
| `share.$token` | brandIdentity → resource → items/events | one wave per branch; rejection guard for the report-404 branch |
| `app.clients` | roomMemories → room-state wave | both in one second wave |
| `search` | token → collections → plan (serial) | one wave before the warm-cache probe; anonymous path unchanged (constants, zero queries) |

Left alone deliberately: `app.billing` (already one wave; the plan-change
preview await genuinely depends on billing), `app-layout`
(session → workspace → presenceNav is a true dependency chain),
`app.digests` (the plan read is a feature gate for everything after it;
the remaining serial `getDigest` only fires on deep links — low traffic),
API/e2e/presence routes (not perceived-speed surfaces).

**Expected impact:** removes 1–5 serial D1 round-trips per page view. Each
round-trip from the Worker to D1 is roughly 5–15ms when healthy (more under
load), so figure ~10–50ms of TTFB on dashboard, watchlists, account,
share pages, and signed-in search. Not a 10x; it is the difference between
16 queries bounded by the slowest one vs. two stacked waves.

## 2. Skeleton coverage (PERF-2, `b2194c7`)

Audit: every `/app` route whose loader runs more than one D1 query already

**Expected impact:** consistency only; `/app/ops` is operator-facing.

## 3. Caching headers (PERF-3, `aa2c542`)

- **Hashed assets:** verified already `public, max-age=31536000, immutable`
  with `cf-cache-status: HIT` in prod. No change.
- **Public HTML:** the worker previously forced `no-store` on *all* HTML.
  Now GET/HEAD 200 HTML on `/`, `/help`, `/docs`, `/terms`, `/privacy`,
  `/changelog`, `/trust`, `/compare/*`, and `/ads/*` with **no better-auth
  cookie** and no `Set-Cookie` gets `public, max-age=300` + `vary: cookie`.
  Everything signed-in or app/auth/search/share/status-shaped keeps the
  exact no-store posture (the root loader embeds the session in every
  document, so signed-in HTML must never be cacheable).
- **Deliberately no `stale-while-revalidate`** (spec suggested 3600):
  deploys replace the hashed-asset manifest, so HTML served stale after a
  deploy references assets that no longer exist — the 2026-07-13 asset-skew
  incident class, and exactly what the existing "stale cached public HTML"
  regression test protects. `max-age=300` bounds that window to 5 minutes;
  SWR would stretch it to an hour. New tests cover the allowlist, the
  cookie/Set-Cookie/non-200/non-GET exclusions, and the SWR-free policy.

**Expected impact:** repeat anonymous views within 5 minutes skip the origin
entirely (~450–700ms saved per view at observed prod TTFB). First views are
unchanged — Workers responses are not edge-cached, so there is no CDN win
to claim here.

## 5. app.css size (PERF-5, `34ff50f`)

**191,035 → 165,758 bytes (−25,277, −13.2%).** Grep-verified with a parsed
rule list (a class counted dead only at zero occurrences across `app/`;
`is-*` names excluded as dynamically composed `is-${state}`):
146 whole rules from legacy pre-rebuild families (old search page
`f9-search-*`, old market board `f9-market-*`, old onboarding, old

dark-theme + media variants), dead parts trimmed from shared comma lists,
and `.f9-search-page .f9-search-*` override rules keyed on
never-rendered descendant classes. Existing rebuild tests assert these
class names are absent from the routes, confirming the deletions.
Zero dead class references remain.

**Expected impact:** ~25KB (~8KB gzipped, estimated) less CSS to download
and parse on cold loads.

## 6. D1 query shape (PERF-6)

N+1 audit of the hottest paths:

- The data layer batches id-list reads via `queryIn` /
  `chunkForBoundParams` (`app/lib/d1-chunk.server.ts`, ≤90 params) with
  `Promise.all` over chunks — `listAdsByIds`, creative hydration
  (`ad-persistence.server.ts`), and the creative wall all already use it.
  **No un-batched loops-of-awaits found in dashboard or search loaders.**
- The dashboard counter-move follow-ups loop is offset pagination with an
  early break (dependent reads, one page in the common case) — not an N+1.
- One real fix: `buildCompetitorDossier` ran two query waves where the
  second was independent — now one 4-query wave (watchlists detail page
  hot path); the not-enough-history case spends two extra cheap reads.

**Expected impact:** one less serial D1 round-trip on the watchlists
detail page.

## Deliberately skipped

- **Edge-caching HTML via the Cache API**: real first-view win for `/ads/*`
  SEO traffic, but cache-key country handling (`cf-ipcountry` feeds the
  snapshot) and deploy-time invalidation need a design pass — not a polish
  commit.
- **`app.clients` per-room `revalidateRoomApprovals`** (up to 50 parallel
  queries): parallel already, but batching needs a data-layer rewrite of
  approval revalidation; clients page is not hot enough to justify it here.
- **`app.digests` deep-link `getDigest` serialization**: low traffic.
- **Dynamic-import consolidation in loaders** (`await import` chains):
  Vite resolves these at build time into the server bundle; no runtime
  round-trip to save.
- **Live browser verification** of these changes: not possible in this
  headless worktree session (no dev-server E2E run); covered by the full
  unit/route suite and left to the reviewer's live pass after integration.
